# 写文章（客观朴素 · 科普 / 描述性）

目标：**让读者用最少的力气，准确理解一件事**。不是展示文采，不是说服，不是带货。

三句话记住风格：

1. **客观**——只写站得住的事实；事实、观点、推测分开写；有来源就给来源。
2. **朴素**——用日常语言、短句、少形容词；不堆术语，不喊口号。
3. **科普 / 描述**——从读者已知的地方出发，一次讲一个新概念，讲清「是什么、为什么、怎么用、边界在哪」。

## 流程

### 0. 先确认交付参数

不清楚就问（一次问完），清楚就直接写：

- **读者是谁**：完全外行 / 有相关背景 / 同行。
- **发在哪**：公众号 / 博客 / 知乎 / 内部文档 / 纯 Markdown 稿。
- **写多长**：几百字的说明，还是几千字的长文。
- **要讲清什么**：一句话说出文章的核心结论。
- **素材从哪来**：用户给的资料 / 指定链接 / 需要自己检索。

用户已经给了足够信息时，**不要为了走流程而提问**，直接产出初稿更受欢迎。

### 1. 先把事实收集齐（关键步骤）

写作前先有一份「事实底稿」，否则一定会编。

- 用户提供的材料优先，**先读完再动笔**。
- 需要外部信息时用搜索或抓取（可配合 `web-content-fetcher` 这类抓取 skill），**逐条记录 URL 和访问时间**。
- 每条关键信息标注类型：**事实 / 观点 / 推测 / 数据**。
- 数字要有**单位、时间、口径、来源**；找不到来源的数字不要写。
- 有争议的话题，写出主流分歧，不要只挑一方。
- 拿不准的，要么核实，要么在文中明说「目前没有定论」或「我没有找到可靠来源」。

### 2. 列提纲

标准骨架（按题材裁剪，不要求每篇都齐全）：

1. **导语**（2–3 句）：这篇讲什么、结论是什么、为什么值得看。
2. **背景**：读者需要先知道的前提，尽量短。
3. **主体**：分 2–5 节，每节一个明确的小结论。小标题直接写结论，比写名词更好读。
4. **边界与局限**：适用范围、反例、已知问题、还没解决的部分。
5. **小结**：回收导语的结论。别升华，别喊口号。

用户没要求就先不单独交提纲，直接给初稿；用户说「先给提纲」就先交提纲。

### 3. 写作规则

**必须做到：**

- 结论先行，一段说一件事。
- 长句拆短；能用主动语态就用主动语态。
- 术语第一次出现，用一句大白话解释，必要时附英文原文。
- 举例优先于下定义；用类比时要说明类比的局限。
- 每个小标题下先给结论，再给理由和证据。
- 具体优于抽象：能写「耗时从 800ms 降到 120ms」，就不写「性能大幅提升」。
- 承认不确定和不知道。

**不要出现：**

- 营销腔与互联网黑话：赋能、抓手、闭环、生态、颠覆、革命性、王炸、天花板、降维打击、yyds、干货、保姆级、一文读懂。
- 空话开头 / 结尾：「在当今这个 XX 的时代」「随着 XX 的飞速发展」「让我们一起……」「总而言之，XX 是大势所趋」。
- 没有信息量的副词堆叠：非常、极其、十分、大大、显著。
- 强行排比、强行升华、感叹号。
- 编造的数据、引用、案例、人物。
- 「值得注意的是」「众所周知」这类填充词，除非真的需要提醒。

**灰色地带：** 第一人称、幽默、个人经历都可以用，但必须服务于「讲清楚」，不能让文章变成自我表演。用户明确指定了语气时，以用户要求为准。

更细的规则、词表和改写对照见 [references/style-guide.md](references/style-guide.md)。骨架模板见 [assets/article-template.md](assets/article-template.md)。

### 4. 自检（交付前逐条过）

- [ ] 核心结论在导语里说清楚了吗？
- [ ] 每个数字 / 事实都有来源吗？没来源的删了吗？
- [ ] 事实、观点、推测区分开了吗？
- [ ] 术语都解释了吗？外行能读懂吗？
- [ ] 黑话、空话、填充词删干净了吗？
- [ ] 有没有为了凑字数写的水段？删掉后文章更短更好吗？
- [ ] 小标题是否准确反映本节内容？
- [ ] 结尾是在升华 / 喊口号吗？改回陈述。
- [ ] 有没有前后矛盾？

### 5. 交付

- 产出 Markdown 文件，文件名用英文短横线 slug，例如 `how-dns-works.md`。
- 文末附「参考来源」列表：标题 + 链接 + 访问时间。
- 回复里给出：文件路径、字数、一句话说明，以及还需要用户确认的点（如有）。

## 写微信公众号（图文并茂）

用户说「写微信公众号」「公众号文章」「推文」时，在以上流程基础上**额外**做这几件事。完整清单、尺寸和排版细则见 [references/wechat.md](references/wechat.md)，配图清单模板见 [assets/figure-plan-template.md](assets/figure-plan-template.md)。

1. **先出配图清单**：每张图写清——位置、要表达什么、类型（流程图 / 示意图 / 数据图 / 截图 / 照片 / 插画）、图注。
2. **能自动生成的图直接生成**，不要留给用户：
   - 流程、结构、时序 → Mermaid，用 `@mermaid-js/mermaid-cli` 渲染成 PNG；
   - 示意图 → 手写 SVG；
   - 数据图 → matplotlib 或图表库；
   - 界面、网页 → 浏览器自动化截图（如 Playwright）。
   - 图片输出到文章目录的 `images/`，命名 `fig01-xxx.png`。
3. **生成不了的图**（照片、插画、氛围图）：给出**中英双语 AI 配图提示词**，在正文对应位置放占位 `![图N：说明](images/figN-xxx.png)`，并在 `prompts.md` 里汇总。
4. **封面图单独设计**：2.35:1（例如 900×383），给出标题文案和生成方案或提示词。
5. **排版按公众号习惯**：段落 1–3 句、多留空行、小标题清晰、加粗克制、少用列表、代码用图片、**不放外链**（公众号外链受限，改为可搜索的名称或来源说明）。
6. **交付目录**：

```
<article-slug>/
├── article.md        # 正文，含图片占位和图注
├── images/           # 已生成的图
├── prompts.md        # AI 配图提示词（中英）
└── sources.md        # 事实来源
```

7. **图片版权**：优先自制；用外部素材必须确认许可，并在图注或文末标注来源；不确定就不要用。
