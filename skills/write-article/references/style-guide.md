# 风格细则（客观朴素 · 科普 / 描述性）

配合 [SKILL.md](../SKILL.md) 使用。这里是可执行的判定标准和对照例子。

## 1. 三条判定线

写完任何一句话，问自己：

1. **它是不是事实？** 不是事实就标明是观点还是推测。
2. **删掉它，读者会损失信息吗？** 不会就删。
3. **一个外行能读懂吗？** 读不懂就换说法或补一句解释。

三条都过，才留下。

## 2. 句子与段落

- **一段一个意思。** 段落超过 5 行就考虑拆开。
- **句子尽量短。** 一句话里超过两个逗号，通常可以拆成两句。
- **主语明确。** 避免"通过这种方式，使得……"这种没有主语的句子。
- **少用名词化。** 「进行优化」→「优化」；「做出决定」→「决定」；「对性能进行提升」→「提升性能」。
- **主动优先。** 「配置被读取后……」→「程序读取配置后……」，除非施动者不重要。
- **具体化。** 「很多」→ 给数字或比例；「最近」→ 给时间；「很快」→ 给量级。
- **一段的开头就给出结论。** 不要让读者读到段尾才知道你要说什么。

## 3. 词表

### 直接删掉的黑话

| 不写 | 换成 |
| --- | --- |
| 赋能 | 让……能做到…… |
| 抓手 | 方法 / 切入点 |
| 闭环 | 完整流程 / 从 A 到 B 都能跑通 |
| 生态 | 相关的工具和社区 |
| 颠覆 / 革命性 | 说清具体改变了什么 |
| 王炸 / 天花板 / 降维打击 | 直接说效果和对比 |
| 干货 / 保姆级 / 一文读懂 | 删掉，标题写清内容即可 |
| yyds / 绝绝子 / 炸裂 | 删掉 |

### 直接删掉的开头与结尾

- 「在当今这个 XX 飞速发展的时代……」
- 「随着 XX 的不断发展，越来越多的人开始关注……」
- 「让我们一起走进 XX 的世界。」
- 「总而言之，XX 是大势所趋 / 未来可期。」
- 「希望这篇文章能对你有所帮助。」（可留一句朴素的，但不要煽情）

### 填充词（除非真的需要提醒，否则删）

- 值得注意的是 / 需要指出的是 / 不难发现 / 众所周知
- 事实上 / 实际上（大多数时候是废话）
- 在一定程度上 / 某种意义上（要么说清程度，要么删）

### 无信息量的程度副词

非常、极其、十分、格外、大大、显著、空前、前所未有。

**处理办法**：要么给出数字，要么直接删。

## 4. 改写对照

### 例 1：空话开头

> ❌ 在当今互联网高速发展的时代，缓存技术已经成为每一位后端工程师必须掌握的核心技能。

> ✅ 缓存的作用是把重复的读请求挡在数据库前面。用得好，接口延迟能从几百毫秒降到几毫秒；用不好，用户会读到过期数据。

### 例 2：无依据的夸大

> ❌ 经过这次优化，系统性能得到了大幅提升，效果非常显著。

> ✅ 同一份数据，改造前 P95 延迟 820ms，改造后 130ms。（本机压测，100 并发，5 万次请求）

如果拿不出数字，就写清楚变化本身：

> ✅ 改造后，原本每次请求都要查一次数据库的步骤被去掉了。

### 例 3：术语不解释

> ❌ 我们使用布隆过滤器来解决缓存穿透问题。

> ✅ 缓存穿透指查询一个数据库里也不存在的 key，结果每次请求都落到数据库上。布隆过滤器是一种概率数据结构，它能确定地说「这个 key 一定不存在」，于是可以在查缓存之前就挡掉大部分无效请求。代价是它有很小的误判率，可能把存在的 key 误判为不存在。

### 例 4：堆形容词

> ❌ 这是一个非常强大且极其优雅的解决方案。

> ✅ 这个方案的好处是不用改表结构，代价是多一次网络往返。

### 例 5：观点冒充事实

> ❌ Rust 是最好的系统编程语言。

> ✅ Rust 在编译期检查内存安全，代价是学习曲线较陡。它是否适合你的项目，取决于团队经验和性能要求。

### 例 6：升华结尾

> ❌ 总而言之，技术的进步永无止境，让我们拥抱变化，迎接更美好的未来！

> ✅ 这套方案适合读多写少、能容忍秒级不一致的场景。如果业务要求强一致，直接读主库更简单。

### 例 7：填充词与冗余

> ❌ 值得注意的是，众所周知，配置文件必须放在项目根目录下。

> ✅ 配置文件必须放在项目根目录下。

### 例 8：类比要标注局限

> ✅ 可以把 DNS 想成电话簿：你报一个名字，它给你一个号码。区别是 DNS 的记录会变，而且缓存在很多层，所以改了记录不会立刻对所有人生效。

## 5. 事实与来源规范

### 来源分级

1. **一手来源**：官方文档、规范原文（RFC、标准）、源码、论文、官方公告、你自己实测的结果。
2. **二手来源**：权威媒体报道、技术博客、教材。
3. **转述与传言**：社交平台帖子、未署名的"据说"。

写作时**优先引用一手来源**。只能找到三手信息时，在文中说明。

### 标注方式

- 正文中提到关键数据或结论时，就近给出来源，例如：「（来源：RFC 9110 §10.1.5 : https://www.rfc-editor.org/rfc/rfc9110#section-10.1.5）」。
- 文末统一列「参考来源」，每条一行，格式见下一节。
- 引用他人原话要加引号并注明出处，不要改写成自己的话再当作事实陈述。
- 实测数据要写清环境：机器、版本、样本量、测量方法。**不写环境的性能数字没有意义。**

### 链接的写法

文章里出现链接的地方——正文引用、参考来源、`sources.md`——统一写成 `标题 : URL`。

冒号用英文半角，**前后各留一个空格**。例子：

```
- RFC 9110 : https://www.rfc-editor.org/rfc/rfc9110
- Lakr233/vphone-cli : https://github.com/Lakr233/vphone-cli
- Node.js 20 发布说明 : https://nodejs.org/en/blog/release/v20.0.0
```

要点：

- 标题写清这是什么，不要只写域名，也不要写「点击这里」。
- **不要**只丢一个裸 URL（`https://...`），也**不要**用 `——`、`·`、`-`、`→` 之类的符号连接标题和链接。
- 访问时间不逐条挂在后面，在列表开头统一说一句：「以下链接均于 2026-09-14 访问。」
- 不写 markdown 行内链接 `[标题](URL)`：公众号里不可点，纯文本稿里也没有必要。用户明确要求可点击时才用。
- 这条规则只管文章产出。skill 自己文件之间的引用（`references/xxx.md` 这类相对路径）继续用 markdown 链接，那是给 agent 读的。

### 不确定时怎么处理

| 情况 | 写法 |
| --- | --- |
| 多方说法冲突 | 「X 认为……；Y 认为……。目前没有定论。」 |
| 只有一条弱来源 | 「据 <来源> 称……」（明确是转述） |
| 自己推测 | 「这可能是因为……」（用「可能」「推测」） |
| 完全查不到 | 不写。不要用常识脑补。 |

### 明确禁止

- 编造数据、引用、案例、人名、机构名。
- 把一篇博客的观点写成「研究表明」。
- 把旧数据当成当前数据（注意年份）。
- 用「据说」「有专家表示」掩盖没有来源。

## 6. 结构模板

### 科普文

```
# 标题（写清讲什么，不做标题党）

导语：2–3 句，结论先行。

## 它是什么
一句话定义 + 一个例子 + 术语解释。

## 为什么需要它 / 它解决什么问题
背景，控制在 3 段以内。

## 怎么工作
分 2–3 个小节，每节一个机制。配图或例子。

## 边界与代价
什么情况下不适用，有什么代价，常见误解。

## 小结
回收导语结论，2–4 句。不升华。

## 参考来源
以下链接均于 YYYY-MM-DD 访问。
- 标题 : https://…
```

### 描述性文章（介绍一个东西 / 一次经历 / 一个现象）

```
# 标题

导语：我看到了什么，它意味着什么。

## 背景
读者需要知道的前提。

## 我观察到的
按时间或按方面分节，只写事实和可验证的细节。

## 这说明什么 / 我还不确定什么
区分观察、解释、猜测。

## 小结

## 参考来源
```

### 技术说明文

```
# 标题

导语：这个方案解决什么问题，结论是什么。

## 问题
可复现的场景与现象。

## 方案
关键设计决策，以及为什么这么选。

## 取舍
替代方案、代价、适用边界。

## 怎么用
最小可复制的步骤或代码。

## 小结
```

标题的要求：**看完标题就知道文章讲什么**。可以用「问题 + 结论」的形式，例如「为什么改了 DNS 记录，本地还是解析到旧 IP」。不要用悬念式标题。
